# 桃山学院大学テック部 会則

会則を読み、変更をPull Request（PR）で議論・記録するためのリポジトリです。テックハックは別組織で、この会則の対象に含めません。

## 本文と閲覧ページ

```text
rules/                  会則・細則のMarkdownと一覧情報
  constitution.md       会則本体
  regulations/          交通費・予算・関係の各規則
  index.json            表示名・状態・出典・日付
site/                   SvelteKit（JavaScript）の閲覧ページ
decisions/              公開できる決議概要と本文ハッシュ
proposals/              未承認の改定趣旨・判断事項
docs/                   移行記録・管理設定の手順
scripts/                本文ハッシュの取得
.github/                PRテンプレート・CI・公開ワークフロー
```

本文の編集先は `rules/` です。`site/` に本文を複製せず、ビルド時に同じMarkdownから静的ページを生成します。文書の追加時はMarkdownを置き、`rules/index.json` に一覧情報を追加してください。ブラウザーのファイル編集からもPRを作れます。

公開URL候補: <https://momoyama-tech.github.io/rules/>。Pagesは別途有効化するまで公開されません。

## 現行文書と移行

- 会則本体は現在使用しているGoogle Docからの移行版です。原文の制定・施行日は2023年10月1日、本文末尾の改正記録は第5条（2024年7月29日）です。
- 交通費・予算・関係の3規則は原文に「起草」とあるため、採択・施行状況を「確認中」と表示します。
- 移行PRでは条文の意味を変えず、条番号の見出し化・箇条書き・改行のみ整えます。誤記や権限の不整合は別の改定PRで扱います。
- 原本と照合方法は [移行記録](docs/migration.md) に記載します。

## PRレビューと正式承認

GitHubのApproveは、正式決議を反映してよいかの確認です。Approveの人数を部員総会の賛成票数に読み替えません。

| 変更 | PRレビュー | 正式承認 |
| --- | --- | --- |
| 会則本文 | 原則2名。決議確認担当と技術確認担当を別人で各1名 | 部員総会の決議 |
| 交通費・予算・関係の細則 | 原則2名。金銭関係は会計担当の確認も記録 | 現行文面では幹部会。採択状況と委任関係の確認が前提 |
| デザイン・リンク・ビルド | 原則2名 | 会則の意味を変えなければ総会決議は不要 |
| 承認手順・管理権限 | 原則2名 | 正式承認の権限を変える場合は、その権限を定める会議の決議も必要 |

作成者を除く2名が最終レビューします。会則の誤字修正も当初は改定として扱い、軽微修正の委任をするなら先に正式決議します。担当者・GitHubチームはまだ未指定です。細則の承認主体の整理は未確定であり、このREADMEだけで現行会則を変更しません。

### 会則改定の流れ

1. 改定PRを作り、理由・新旧差分・影響条文・判断事項を示す。
2. 投票対象の本文、比較元の版、PRのコミットを固定する。`npm run rules:hash` で本文のSHA-256を取得する。
3. 現行会則に従い、部員総会などの正式決議を行う。
4. 正式議事録をNotionに記録し、公開可能な決議概要を `decisions/` に追加する。
5. 決議確認担当が原議事録を読み、議決条件・結果・本文ハッシュ・施行日を照合する。別の技術確認担当が差分と画面を確認し、最終版に2名がApproveする。
6. 施行日に合わせて `main` にマージし、公開する。将来施行の改定は施行日までPRに保持し、現行版を公開し続ける。

正式議事録には、決議日・機関・適用条項・定足数の成立・出席者数・賛成／反対／棄権／無効票数・施行日・対象PR・比較元の版・投票対象本文のハッシュを記録します。公開版は個人を識別しない決議概要と文書識別情報に絞り、非公開記録とは決議IDで対応させます。

ハッシュ対象は対象MarkdownのUTF-8の生バイトです。決議ファイル自身は対象に含めず、自己参照を避けます。決議後に本文が変わったら再審議に戻します。決議情報だけの追加でもPRレビューは最新コミットに対してやり直します。他の改定が先に成立した場合は比較元と全文を再照合します。

CIは記録の形式や本文一致の検査を補助できますが、総会が実際に成立したかは人が原議事録を確認します。「承認済み」ラベル・チェック欄・CI成功だけでは正式承認になりません。

### 先に確定する議決条件

現行第15条は「賛成6:反対4」と記載しています。60%ちょうどを含むか、分母が参加者全員か有効投票数か、棄権・無効票、定足数、オンライン投票・委任の扱いは文書から確定できません。「過半数」や「3分の2」に置き換えません。

第10条の「部会」と部員総会、第11条の顧問・部長・外部顧問の議決権との関係、細則の採択状況も正式に整理します。案は [proposals/](proposals/) に置き、採用前は現行規則と区別します。案の採決にも、その案自身の新しい条件ではなく現行の手続を使います。

## GitHubで設定する保護ルール

**READMEの記載だけでは保護は有効になりません。初期PR作成時点では未設定です。** 実設定と拒否テストを [管理設定チェックリスト](docs/github-setup.md) で確認してから運用を始めます。

- `main` のリポジトリ単位RulesetをActiveにし、PR・Approve 2名・議論の解決を必須にする。
- 変更時に古いApproveを失効させ、最後にpushした人以外の承認も要求する。
- 会則・決議記録は決議確認チームと技術確認チーム各1名のレビューを必須にする。2名は別人とし、役割の重複で1人を2人と数えない。
- 数えるレビュアーには当該リポジトリのwrite以上が必要。部員全員にwriteを付与せず、forkからの提案も受け付ける。
- CIの `site-checks` を必須にする。これは本文・画面・ビルドの検査で、正式決議の自動判定ではない。
- force push・main削除を禁止し、通常の管理者バイパスを設けない。レビューの却下解除権限も限定する。
- CODEOWNERS自体・ワークフロー・検査スクリプトもレビュー対象にする。担当確定後に `.github/CODEOWNERS.example` を編集・改名する。

CODEOWNERSに2チームを書くことだけでは両チーム必須になりません。Rulesetsのチーム別Required reviewersで設定し、利用できない場合は代替検証を決めるまで同等の保護と扱いません。管理者は設定自体を変更できるため、設定変更の記録と相互確認も必要です。

参照: [Rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets) / [CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)

## 記録と公開範囲

- Notionは正式な決定と案件管理の正本、GitHubは決議済み本文の版管理先、Pagesはその閲覧面とする。
- 移行の正式採用まではGoogle Docを参照元とする。採用後の保存・閲覧権限は別途決め、独立した現行版を二重に編集しない。
- PublicではPR・コメント・コミット履歴も公開対象。公開するのは会則、公開可能な改定理由・決議概要・履歴とする。
- 名簿、個人別投票、精算証憑、個別相談・処分記録、認証情報は入れない。原文の起草者名・Docコメントも初期移行には含めない。
- 運用採用・PR作成・タスク登録を、総会決議・マージ・公開・外部送信の承認と読み替えない。

## ローカルで見る

Node.js 24 LTSを使用します。実装はJavaScriptとSvelte、JSDocと型宣言は検査用です。

```sh
npm --prefix site ci
npm run dev
```

表示されたローカルURLを開きます。本文の編集後は画面を再読み込みしてください。

```sh
npm run check
npm test
npm run build
npm run preview
```

成果物は `site/build/`。Pagesと同じサブパスで検証する場合:

```sh
BASE_PATH=/rules npm run build
BASE_PATH=/rules npm run preview
# 表示されたローカルURLの /rules/ を開く
```

## GitHub Pagesへの導入

SvelteKitのstatic adapterで全ページを事前生成します。サーバーやDBは不要です。

初回公開は別途承認後に行います。管理チェックリストを完了し、Pages SourceをGitHub Actionsにし、`github-pages` environmentをSelected branchesで明示的に `main` のみに制限します。Repository variable `PAGES_ENABLED` を `true` にして、`Deploy Pages` を `main` から手動実行します。変数が未設定なら公開ジョブは動きません。

この段階では手動公開です。mainへのマージ時の自動公開は、正式承認・施行日の運用確認後に別PRで有効にします。PRのCIは公開権限や秘密情報を使用しません。
